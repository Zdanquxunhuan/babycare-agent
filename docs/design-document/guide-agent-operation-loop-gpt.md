# 导购 Agent 如何接住用户的下一句话

**设计评审稿 · 2026-11-27**  
首期场景为本店商品查询中的追加条件、列表选款和误追问纠正。

**设计建议**：让一个导购 Agent 根据购买目标选择行动，读取工具结果，再决定答复、继续核查或澄清。Java 保存已经确认的条件，执行有权限的查询，核验库存和金额。首期把“按条件查一组可以买的商品”作为一次工具调用开放给模型。这样，“要 L 码的”可以一次查完，遇到含混指代或缺货时，模型也有机会根据新信息调整。

## 1. 从顾客应当看到什么开始

| 轮次 | 导购原话 | Agent 应当完成的事 |
|---|---|---|
| 1 | 买两包纸尿裤 | 确认品类为纸尿裤，同一款买两包，按本店可售库存列出候选。截图样本有 22 款。 |
| 2 | 要 L 码的 | 只增加尺码。原先没有品牌限制，返回所有满足条件的品牌，每款给出两包合计。 |
| 3 | 第二款呢？ | 按第二轮实际展示的顺序找到绒朵，再核验这款的库存和价格。 |

第二轮可以直接回答：“按刚才的两包算，本店有 4 款 L 码纸尿裤可选。芽禾两包 212 元，绒朵 238 元，小晴 264 元，沐叶 290 元。”这些是直营店模拟快照按普通价计算的验收值。第三轮中的“第二款”指向 `DEMO-008`，沿用第一轮的包数；如果库存已经变化，回复采用本轮核验结果。[验收用商品样本](../../fixtures/catalog-demo.json)

### 现有程序为什么会卡住

`Guide.answerProduct` 先合并条件，再处理模型给出的商品指代。如果指代是“当前款”、列表有多款且尚未选中，程序会立即返回选款追问。此时 L 码即使已经写进条件，购买检索也还没有执行。`Checkpoints.finish` 会保存追问，展示顺序仍来自前一次成功列出的 22 款。下一轮即使重述同一条件，系统也可能沿着旧追问继续。截图能确认用户看到的回复，无法还原当时百炼返回的原始计划。设计和测试应覆盖这条可由代码确认的失败路径。[商品决策入口](../../src/main/java/com/yu/babycare/agent/Guide.java) · [会话检查点](../../src/main/java/com/yu/babycare/conversation/Checkpoints.java)

## 2. 一轮决策怎样运行

| Agent 能力 | 在本例中交给模型的判断 | 可以观察到的产物 |
|---|---|---|
| 理解 | “要 L 码的”修改哪项需求？用户是否在指某件商品？ | 本轮条件增量为“尺码设为 L”，原话依据为“L 码”，操作对象为列表。 |
| 规划 | 已经知道品类和包数，还缺什么事实才能回答？ | 请求按合并条件查询本店可买的商品。常见购买请求只需一个业务工具。 |
| 决策 | 工具返回 4 款后，是展示结果还是请顾客选一款？ | 购买目标允许多个候选，选择展示完整结果。 |
| 调整 | 如果先前误以为用户选了某款，执行器报告“没有可定位的商品”，接下来做什么？ | 重新读取原话、待答事项和已确认条件，改为查整张列表；若用户确实只说“这款呢”，可请求澄清。 |
| 评估 | 即将展示的结果有没有回答“两包、L 码、哪些可以买”？ | 模型选择回答所依据的工具结果，程序校验该结果对应的条件、数量、列表范围及核验状态。 |

沿用现有门店身份、风险处理及知识／售后路由。第一阶段，新循环接管商品列表和选款路径。已有意图解析可以给出首次行动建议；执行器将原话和检查点一并传入，允许 Agent 在执行前或收到观察后更正建议。联合售后咨询继续通过现有入口组合政策证据。实现评测计入路由和工具内发生的全部模型调用。

一轮内的数据流是 **本轮原话与检查点 → 模型选择行动 → Java 执行或返回可解释的错误 → 模型读取观察 → 返回结果、继续调用或询问**。每次调用只要求模型给出下一项可执行动作、条件变更及其原话依据。执行记录足以复盘一次选择。

## 3. 给模型什么上下文，允许它做什么

**跨轮上下文。** 读取当前门店、确认过的购买条件、上一张列表的有序商品编号、已选中商品、上轮待答事项。需要理解“绒朵那个”“最后一款”时，附上已展示条目的序号、品牌、品类、尺码等简短描述。展示顺序由服务端提供。上次的价格和库存带有历史时点，本轮报价重新查询。

**条件变更。** 每项条件支持沿用、设置和清除。未提品牌就沿用既有偏好。明确说“品牌全都可以”可以清除原先的品牌限制；“芽禾也可以，但还是不要绒朵”只放开芽禾，保留对绒朵的排除。数量、单包预算、总预算和活动口径继续按已有规则合并。即使旧检查点已经存了 L 码，用户重新表述购买目标仍可触发查询，是否执行查询由本轮行动决定。

| 拟提供的行动 | 输入与执行 | 返回给模型的观察 |
|---|---|---|
| 查询列表 | 模型给出条件增量及依据，服务端合并后在本店目录重查。已知包数就批量核验同款数量和报价。可以查到刚放宽品牌后新符合条件的商品。 | 本轮结果编号、有效条件、按展示顺序排列的候选、库存和报价口径；区分成功、核实无匹配、库存未知与人工核验。 |
| 核验某款 | 模型给出所指列表、指代原话、拟选条目及本轮购买条件。服务端按已展示列表解析序号或校验属性匹配，再核验商品。 | 已核验的单款结果，或“无选中款”“序号越界”“多款符合描述”等观察。 |
| 答复或澄清 | 展示商品时引用本轮结果编号；澄清时说明哪项信息缺失，以及它会改变哪项决定。 | 验证通过即生成现有网页支持的回复；证据、条件或结果不一致时，反馈具体问题供模型修正。 |

拟从 `Catalog`、`PurchasePlanner` 复用批量查询和库存、金额核算逻辑。首期的工具粒度允许一次核验完整列表。普通价核算和活动核算各自保留来源、状态和时点。执行器从账号注入门店，从检查点解析可引用的商品；最终商品、包数和金额由核验结果填入现有回复字段。[商品目录](../../src/main/java/com/yu/babycare/catalog/Catalog.java) · [购买核验逻辑](../../src/main/java/com/yu/babycare/agent/PurchasePlanner.java)

## 4. 当模型理解错时如何恢复

假设第二轮模型提议核验“当前款”，同时提取到尺码 L。执行器发现列表有 22 款、已选中商品为空，先向模型反馈“当前款无法定位”，并保留原话和 L 码增量。此时无需让导购做任何操作。模型可以重新选择列表查询，获得 4 款后答复。**失败的选款尝试不写入跨轮状态。**

有三个相邻场景需要单独看待：

- **明确指代。** “第二款买三包”同时含有序号和包数，按展示顺序定位，再按三包核验。若用户说“第二款有 L 码吗”，先查清第二款所指商品；同品牌同品类有可核实的 L 码规格时可列出，并标明不同的商品编号。所指商品与所求规格确有歧义时，只询问影响结果的区别。
- **真实歧义。** 在没有已选中款的多款列表中说“就它吧”，模型有理由追问。若顾客接着说“我是说所有 L 码的”，本轮购买目标可以解除旧追问。历史追问只提供上下文，不能要求顾客必须回答一个序号。
- **工具反馈。** 同一请求分别遇到“还有两包”“只剩一包”“库存系统超时”，应分别得到可买结果、数量不足的说明、库存待确认。模型根据用户已授权的品牌偏好决定是否搜索替代。任何放宽尺码、数量或硬预算的方案，都需要用户先改变相应条件。

**循环边界。** 试点初值建议每轮至多 4 次模型调用、4 次业务工具请求，共用 30 秒截止时间，计入路由和工具内调用。这些是待压测的预算。相同条件下的相同调用可复用本轮观察。无效行动允许带错误详情重规划一次。再次无进展时，如果已有与当前目标一致的核验结果，直接呈现；库存未知则明确提示待核验；缺少会改变结果的信息才询问该项。无有效结果且执行预算已耗尽时，返回现有未完成状态，允许重试。整轮模型服务不可用时沿用现有服务错误与租约释放机制。

## 5. 状态何时提交

工具结果先放在本轮工作区。只有面向用户的终态通过校验后，才使用现有 `claim/finish` 机制按消息编号和会话版本一次提交。网络重试复用已提交结果。模型等待及库存核验在检查点事务之外执行。

| 本轮结果 | 下轮读取的状态 |
|---|---|
| 成功筛选 | 保存合并后的条件，用实际展示的 4 款及其顺序替换旧列表，清除旧选中款和已解决的待答事项。核实为空时保存空列表。 |
| 成功选款 | 保存选中商品和新的包数等条件，保留供序号继续引用的原列表顺序。 |
| 有必要的澄清 | 保存已确认的部分条件、待答原因、所指列表版本及本次问题。检查点缺少新增字段时，以已有条件和已展示列表恢复；旧追问文本可供理解。 |
| 查询中断或库存未知 | 不把失败写成零库存或空列表。保留最后实际展示的列表及其指代范围，将本次未核验需求与该列表区分，以便“再查一次”继续核验。 |

## 6. 框架选择和第一步验证

**推荐在商品路径试用 LangChain4j 的低层 ChatModel 工具调用，继续使用百炼。** 项目已经用 Java 封装了目录、库存和报价，也有面向百炼的购买规划草案。低层接口可以显式传递工具请求及对应结果，便于注入“第一次选错款”、限制耗时和检查第二次决策。Spring AI 的 `ChatClient` 与工具调用循环也适合实现同一设计。继续使用当前 HTTP 客户端则需要项目自行维护工具声明、请求编号、结果回传和重试。框架选择影响接入成本，实际模型能否理解纠正要通过对话评测判断。[LangChain4j 工具调用](https://docs.langchain4j.dev/tutorials/tools/) · [百炼适配器](https://docs.langchain4j.dev/integrations/language-models/dashscope/) · [Spring AI 工具调用](https://docs.spring.io/spring-ai/reference/api/tools.html) · [项目购买规划草案](langchain4j-purchase-planner.md)

第一步在隔离的模拟门店验证项目 JDK、Spring Boot、百炼模型与适配器确能往返一次工具调用，保留请求编号、观察状态与后续动作。先接“列表查询”和“核验某款”，用一个门店开关对照当前商品路径。完成本例验收后，再决定是否让复杂替代和组合购买也采用同一循环。

## 7. 怎样判断 Agent 确实起了作用

| 验收对话或实验 | 可核对的通过条件 |
|---|---|
| 买两包纸尿裤 → 要 L 码的 → 第二款呢 | 第二轮完整返回模拟直营店的 4 款及两包合计；第三轮核验绒朵。两轮都直接回答。 |
| 从截图中的旧追问恢复 → 我的意思是要买 L 码的两包纸尿裤，不限制品牌 | 即使已存 L 码、旧列表仍有 22 款，也重新查询并更新列表。 |
| 只看绒朵 → 要 L 码的 → 品牌全都可以 | 先保留原品牌，再放宽品牌范围；品类和包数从已确认的购买任务继承。 |
| 就这款吧 → 第二款；另测第 23 款 | 多款且无焦点时澄清；给出有效序号后恢复；越界时说明可选范围。 |
| 注入错误的“当前款”调用 | 工具返回定位失败，模型随后请求列表查询并完成回答。调用轨迹能显示模型确实读到了错误观察。 |
| 同一句“绒朵 L 码两包，其他牌子也行”，分别设置库存为两包、一包、查询超时 | 在已确认品类的会话中，观察后续行动分别为给原款、查询合规替代、说明库存待确认。核对实际请求和最终结果。 |

分两组举证。模型替身测试固定错误指代、并发重试、旧检查点和工具失败，验证执行器行为。真实百炼测试使用相同门店样本，并加入未出现在提示词中的口语、纠正和改口。对照当前流程记录**任务成功率、多余追问率、误判恢复率、每轮模型调用数及 P95 耗时**。任务成功要同时核对商品集合、数量、金额和下一轮指代。记录每次操作、条件增量、工具状态与最终选择，区分由模型重规划成功和由程序回退完成的样本。评审启用范围时同时看任务收益和等待成本。
