# BabyCare Agent · LangChain4j 购买规划器设计

状态为待开发。适用场景是本店购买任务中，顾客的品牌偏好、预算和可售库存影响下一步买法。先交付“要 L 码的”列表筛选纠错，再实施此方案。

## 从导购的一个问题开始

“今天带走两包 L 码纸尿裤，最好能留一包绒朵，其他牌子也行，总共 220 元。”在本店模拟样本中，先找到原款并核验库存。库存充足且两包活动价 218 元时，可直接给出原款方案。仅剩一包时，比较保留一包原款的组合和整单替代。芽禾两包 212 元符合预算，绒朵加芽禾共 225 元，保留偏好要多 5 元。顾客再说“最多加 10 块”时，总预算变成 230 元，重新查两款的库存和价格后再答复。把“最好”换成“必须保留一包”时，两包芽禾不能列为合格方案。

## 接入位置与框架选择

沿用 Guide 的门店权限、商品任务理解与条件合并。明确的列表筛选、列表选款、单款核价仍由现有入口处理。购买意图在本轮表达了组合比较、缺货后的多种买法，或在继续一个未结束的组合购买任务时，Guide 将原话、结构化目标和授权上下文交给拟新增的 MixedPurchasePlanner。沿用已有 MIXED_BASKET 意图，补充对隐含比较和预算续问的语义识别。按任务类型和检查点路由。现有 LanguageModel.firstCheck 服务于固定购买流程；它只返回首项工具，签名不足以传递模型的工具请求与后续结果。

新规划器用 LangChain4j 的低层 ChatModel API。拟引入 dev.langchain4j:langchain4j-community-dashscope，以普通 Java 依赖在 Spring 中构建 QwenChatModel，使用百炼北京地域、qwen-plus、服务端环境变量 DASHSCOPE_API_KEY。原 BailianModel 的兼容接口地址与原生 DashScope 的服务地址分别配置。首个开发切片用项目 JDK 21 和 Spring Boot 4.2.0 核实依赖树、实际工具调用及超时配置，锁定实测可用的依赖版本。现有问答、RAG 与引用继续走既有实现。

## 一个模型轮次如何执行

1. 从检查点提取硬条件、可放宽的偏好、最近商品指代、本轮尚待回答的问题，附上导购的本轮原话。Java 以当前授权状态生成 ToolSpecification 清单。模型自行选择下一项只读核验，也可请求澄清或提出最终方案。
2. 通过 ChatRequest 发起调用。返回的 AiMessage 若包含 ToolExecutionRequest，执行器校验名称、参数、候选范围和剩余预算。门店与导购身份由服务端注入。执行后把原 AiMessage 与每个请求对应的 ToolExecutionResultMessage 一起送回模型。同一回复内的多个请求逐项计数、分别关联结果。
3. 模型现在能读到“原款只有 1 包”，再决定是否搜索替代、对哪个组合核价或停止。通过工具生成的方案编号引用报价。最终输出提案包含推荐方案编号、可选取舍、未核实项或一个澄清问题；Java 校验后渲染商品、数量、价格及优惠。若已找到硬条件内可买的方案，就先给出。超预算的选项只能解释取舍。
4. Java 拒绝越权目标、无效 SKU、超出购买数量的组合及未经核验的价格。相同事实上的重复请求复用本轮结果，持续无进展则停止。模型调用、每个工具请求和重试共用本轮截止时间和步骤预算。超限、模型出错或库存未知时，保留已核实部分，说明哪一项需要门店确认。门店切回人工开关优先。

## 首版工具契约

工具名称为拟议接口。范围限定在同店、同品类、同尺码、两包，支持同一 SKU 两包或两个 SKU 各一包。

| 只读工具 | 模型传入 | Java 返回与核验 |
|---|---|---|
| searchProducts | 搜原款或替代品、本轮允许的品牌条件 | 基于 Catalog 和已确认条件，给出本店候选编号、品牌、品类、规格。执行器保留排除条件，校验是否允许跨品牌。 |
| checkStock | 本轮候选编号列表 | 经库存服务读取实际可售包数、查询时点和数据源状态。成功返回 0 与查询失败有独立状态。 |
| quoteBasket | 候选编号和各自包数 | 复用 POS、活动规则和金额核算，生成本轮方案编号、逐项价格、库存可交付性、适用优惠、总价和预算差额。每个 SKU 按自身数量判断同款活动。两个 SKU 各一包不能套用任一款的两包优惠。 |

为防止单款报价被前端误读为整单合计，在 Guide.Reply 拟增加可选的组合方案集合，每个方案含商品行、合计、预算差额、核验状态。网页按方案展示；原 products/totals 继续表达单款。库存超时与活动未核实分别呈现。若不能确定优惠，已核实的普通价须标明口径。

## 状态和评估

Checkpoints 作为唯一跨轮购买状态来源，保存数量、预算口径、品牌是必须或偏好、是否允许混搭、原款与最近展示的组合成员、待答问题及版本。新增字段可缺省，旧会话可以恢复。LangChain4j 的本轮消息序列只服务这次工具调用。下一轮重建最小上下文；报价、库存和活动重新核验。沿用现有 claim/finish、消息幂等和门店隔离，模型等待期间释放数据库事务。

运行时，模型依据顾客目标检查是否漏答品牌偏好或遗漏预算内方案，Java 核对所有推荐的硬条件和证据。已有报价中存在可行方案而提案只给超预算方案时，允许在剩余预算内修正一次，之后可直接展示已验证方案。评测时用独立样本枚举可行组合，额外检查模型是否根本漏查了某个可行选项。记录工具名称、脱敏参数、结果状态、方案编号、时延、调用次数和可得的 token 用量。

## 实施与验收

| 切片 | 可独立验收的交付 |
|---|---|
| 1 · 接通真实工具调用 | 隔离模拟门店，经百炼收到工具请求、执行查库存、回传对应结果。分别设原款为 2 包与 1 包，保留第二次模型响应与调用轨迹，核对模型实际收到了不同观察。 |
| 2 · 接入网页与购买检查点 | 完成“原款两包 218 元”“只剩一包时优先给出 212 元，解释 225 元”“预算加 10 元后可买混搭”三条链路。验证必须留原款、仅限原品牌、库存未知和活动服务异常。刷新后仍可续办。 |
| 3 · 决定启用范围 | 固定策略与 LangChain4j 使用同一工具、组合报价器、模拟门店和独立题集。用未参与提示词调试的口语问法，比较满足硬条件的任务数／总数、遗漏可行买法、多余追问、模型与工具调用数、耗时。错报库存或价格、把超预算当合格、越权取数均为失败。复跑原 8 组多轮、6 条缺货及列表筛选纠错用例，区分替身与真实百炼报告。只有复杂购买路径收益可复现且代价可接受时才设为该类任务默认策略。 |
